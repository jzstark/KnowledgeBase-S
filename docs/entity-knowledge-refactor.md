# Entity 知识页面持续更新实施计划

状态：E1–E5 的代码已在本地实施，等待生产部署和 VPS 数据盘点。下面保留原计划与验收标准；尚未在真实 entity 上执行付费批量重建。

本计划承接 [Document lifecycle](document-lifecycle-refactor.md) 和 [Document intake](document-intake-refactor.md)。领域背景见 [CONTEXT.md](../CONTEXT.md) 与 [资料夹设计](revision-source-folders.md)。[Phase C](phase-c-convergence-plan.md) 中的全文事实源裁决仍是历史提案，不能据此宣称全库 Wiki 已经可以安全重建。

## 1. 用户已经确认的内容原则

**Entity 的内容范围和篇幅由库内有效信息决定。** 模型自行安排结构和详略，正文不设固定字数目标、下限或上限。

- 去掉 entity 生成提示词的 300–600 字、600 字以内等限制，删除所有 entity 正文的 `[:500]` 截断。
- “印度”只有一篇涉及某项政策的文章时，页面只介绍材料支持的相关信息；不自动补充人口、地理、历史等库外常识。
- 后续材料增加不同方面的有效信息时，页面可以自然增加章节与细节。多篇文章重复同一事实时合并内容、补充来源，无需增加篇幅。
- 篇幅不按来源篇数机械增长。一篇信息丰富的材料也可能支持较长页面；大量重复报道也可能只支持短页面。
- 更正旧观点、区分不同时期和记录来源分歧；不把新旧信息简单拼接，也不默认新报道一定正确。
- 正文中的事实性表述应能追溯到库内文章及相关证据。已有 entity 正文用于组织和对比，不能作为未经复核的独立证据。
- 允许单次模型调用的技术限制与任务资源预算。模型因输出额度耗尽而中止时，继续生成或报告任务未完成，不发布半篇正文，也不通过硬截断伪装成功。

## 2. 当前问题与代码证据

| 问题 | 当前代码 | 影响 |
| --- | --- | --- |
| 新文章写了事实，但刷新从另一套关系取来源 | `kb/ingest.py:do_process_entity_candidates` 的已有实体分支写 `entity_facts` 和 stale 标记；`kb/graph.py:lm_refresh_entity_abstract` 只查询 `mentions` 边 | 新贡献可能没有进入生成输入 |
| 自动刷新没有更新页面正文 | `lm_refresh_entity_abstract` 更新数据库 `abstract`；`kb/internal.py:get_node` 和知识页正文读取 Wiki 文件 | 数据库描述变化了，用户看到的页面仍是旧内容 |
| 完整页面和摘要混用 | worker 的 `article_ingestion.py:_promote_entities`、维护任务的 `maintenance/entity_ops.py:promote_entity_candidates` 都传入 `entity_body[:500]` | 初始生成内容不能完整保存在数据库中 |
| 晋升后的描述又被简化 | `mark_candidate_promoted` 和维护晋升调用 `refresh_entity_profile`，用前三条事实拼接覆盖 `abstract` | 生成过的内容可能退化为几句描述，甚至只是“某文章提到了它” |
| 多个写入路径竞争 | worker 写 entity Wiki；`/ingest` 的后台任务也会通过 `write_wiki_node` 写同一个文件 | 文件内容取决于最后完成的写入路径 |
| 输入和输出受过时规则限制 | `config/prompts.md` 的固定字数要求；生成和刷新只读取至多 `max_entity_page_sources` 篇文章摘要 | 库内已有的有效信息可能被排除，正文也被主动压短 |
| 更新通知和完成状态不可靠 | pipeline 结束后调用一次 `refresh_stale`，只处理一批；刷新完成直接将 `abstract_stale` 清为 false | 剩余任务依赖下一轮导入；生成期间的新变化可能被旧任务清掉 |

这些是代码层面的缺口，不代表已经确定每个现有 entity 的具体受损情况。实施第一步需要构造可重复案例，并将 VPS 盘点作为后续独立步骤。

## 3. 目标行为与范围

一次文章入库成功后，相关 entity 的来源关系和更新请求应已持久化。后台任务最终生成完整正文，详情页和 entity Wiki 使用同一份已发布内容。失败时保留上次完整结果，并显示待更新或失败状态。

覆盖首次实体晋升、已有实体新增来源、文章重新生成、永久删除、实体合并、实体手动刷新、维护补建、entity Wiki 重建和旧数据修复。

保持当前候选晋升阈值、实体名称匹配规则及用户组织文档的规则。资料夹移动不改变知识来源；按当前 lifecycle 语义，归档保留知识文章，因此归档本身不撤销 entity 的证据。永久删除文章才移除其贡献。实体合并后将来源归到目标实体，源实体的迟到任务不能再写页面。

文章全文被全库 Wiki 重建覆盖的问题另有范围。本计划只修改 entity 的正文权威位置与渲染，补足读取文章证据所必需的能力，不把修复旧 entity 建立在执行全库 `rebuild_wiki` 上。

## 4. 数据与职责设计

### 4.1 一处记录实体的来源文章

建议新增 `entity_sources`，以 `(entity_id, article_id)` 为唯一键，并通过外键关联现有节点。它回答“这个实体需要参考哪些库内文章”。同一用户和节点类型的约束由 module 在事务内验证。

这张表有具体用途：文章可能只确定提到了实体，暂时没有可用的具体事实；此时应保留来源关系，不再为了建立关联而制造一条貌似事实的占位句。

- `entity_sources` 是 entity 生成、来源列表和来源变更检测的依据。
- `entity_facts` 保存从相应文章获得的事实与证据。旧的“某文提到某实体”记录仅可帮助恢复来源关系，不作为正文知识直接输入。
- `knowledge_edges` 中的 `mentions` 是同一来源关系的图谱表示，由 module 同步维护。后续的 Wiki 链接扫描不能再独立决定正文生成的来源集合。
- 有效来源关联、事实变化、对应图谱边和更新请求在同一数据库事务中提交。重复输入幂等；重新生成按文章替换其旧贡献，不能只追加。
- 实体详情、图谱相关查询和维护回填使用同一来源定义。`fetch_source_node_ids` 中现有 facts、edges、旧 `source_node_ids` 的混合读取需要随迁移收敛。
- orphan 检查也要区分“没有来源”和“有来源但没有具体事实”，避免新关系已建立却仍因 facts 为空被错误标记。

### 4.2 完整正文有独立持久化位置

在 `entity_nodes` 增加完整 Markdown 正文与生成版本字段，正文使用 PostgreSQL `TEXT`。`knowledge_nodes.abstract` 只承担列表、检索等场景的简介，不再作为完整页面的替代品。

最低需要表达：

- `body_markdown`：最近一次完整发布的正文；无正文与正文为空不能混淆。
- `requested_revision` / `published_revision`：请求更新的版本与已完成正文的版本。
- 正文生成时间、使用的来源清单或指纹：用于确认结果对应哪些输入，并核对旧任务。

简介应从本轮已验证的内容独立提炼，保存完整生成结果；不能重新引入 `body[:N]`。正文、简介、相关 embedding 和已发布版本在一个短事务中更新。模型调用在事务外执行。

entity Wiki 是已发布正文与结构化元数据的渲染副本。详情页、entity 公共读取与工具读取统一通过 module 获取正文，保留现有响应字段所需的兼容映射。页面不会因为 Wiki 暂时写入失败而退回旧正文或短摘要。

### 4.3 一个 module 负责 entity 的持续更新

新增 `services/api/kb/entity_knowledge.py`，集中来源协调、证据读取、生成发布和 entity 渲染。worker、HTTP route 和维护入口通过它的 interface 表达操作意图。

| 调用意图 | Interface 承诺 | Implementation 负责 |
| --- | --- | --- |
| 记录或替换文章对实体的贡献 | 返回已提交的来源关联与更新请求 | 事实、来源关系、图谱边、版本和任务协调 |
| 删除文章贡献或合并实体来源 | 受影响实体最终依据剩余有效材料更新 | 收集受影响 ID、清理或转移关联、锁定顺序、安排刷新 |
| 晋升候选或请求实体刷新 | 返回实体和持久化任务信息 | 幂等身份、候选来源回填、任务去重 |
| 执行实体刷新 | 返回已发布、已过时、待续写或失败的明确结果 | 输入快照、证据、模型调用、完整性检查、版本核对、正文发布 |
| 读取或渲染实体正文 | 返回同一版本的完整内容 | 权威正文、旧数据过渡、元数据和 Markdown 输出 |

函数数量和参数按实际调用场景确定。沿用现有 PostgreSQL、模型客户端、文件目录和 jobs；测试在模型调用这一 seam 使用可控制输出的 adapter，不引入通用存储或任务框架。

## 5. 正文生成方式

1. 从完整的来源关系集合建立输入快照，记录文章身份和内容版本或指纹。不再把固定的前 N 篇摘要当作全部知识。
2. 读取每篇文章中与实体有关的证据。摘要可以帮助定位，但不能成为唯一材料；优先使用已保存的提取正文和可定位的相关片段。文章内容按资料处理，不执行其中夹带的指令。
3. 单篇或总材料过长时分段提取证据、去重、再组织正文；分批用于适应上下文窗口，不能静默丢掉后面的文章。读取不完整时记录缺失范围，不将结果标为已完整更新。
4. 结合实体原有完整正文核对新增、更正和删除的证据，生成符合库内材料的结构。仅出现实体名称的文章不应被扩展成一整节背景知识。
5. 给关键事实附上可解析的文章引用，时间变化和分歧保留对应来源。发布前校验引用属于本次有效来源集合，并确保所引用片段存在；事实是否被正确概括还需质量样例评估，不能由引用 ID 存在代替。
6. 检查模型停止原因及结果是否完整。因 token 限制停止时续写或按章节继续，处理重叠段落；所有必要部分完成后才发布。达到任务资源预算仍未完成则保留旧版本，留下可继续或重试的任务结果。
7. 没有任何有效来源时，保留实体身份并明确显示缺少库内材料，不生成百科常识，也不把已经失去来源支持的旧正文当作最新结果。

**生成任务必须等正文可用。** 当前 pipeline 在文章和候选处理后，才通过 source item 成功回调持久化 `extracted_text_ref`。不能在文章记录刚提交时就把尚未发布的正文判断为丢失。实现时明确文章证据的就绪条件与引用发布操作；新导入材料未就绪时任务保持等待，材料发布后继续，并确保书籍章节有各自可读取的正文定位。真正丢失的历史文件与尚未就绪的新材料分开报告。

**书籍章节必须保持证据范围。** 当前 book pipeline 将整本书的提取文本保存在同一 `source_item.extracted_text_ref`，而章节 article 另有正文。证据读取需要识别章节，只使用该章节内容；不能将整本书当作每一章的正文重复引用。缺少可核对的章节材料时标记缺失，不用其他章节填补。

旧文章可能只有 Wiki 正文、只有摘要或正文文件已缺失。盘点和迁移应标明可用证据层级：已有摘要只能支持其中明确表达的有限信息，不能据此宣称恢复了原文细节。需要重新提取或重新抓取的条目单独列出。

## 6. 更新任务、并发和文件一致性

复用 `jobs.py` 与 `job_worker.py`，新增 entity 刷新任务类型。将现在 pipeline 结束后的 best-effort HTTP 刷新改为持久化任务通知；文章相关数据库事务成功前，任务不可被领取。

- 每次有效来源或内容变化增加请求版本。任务键包含实体 ID 与版本，同版本去重；已被新版本替代的排队任务可直接跳过模型调用。
- 初次晋升、自动更新、手动刷新和维护任务走同一执行路径。手动请求即使材料未变，也能明确安排一次新的刷新。
- 生成开始时读取一致的来源快照；发布时再次检查实体存在、未合并、请求版本仍匹配。来源已变化的结果不能覆盖新版本，也不能清掉后续更新请求。
- 生成期间不长时间锁住实体或文章。涉及文章生命周期与实体关联的短事务统一锁定顺序，多个实体按稳定 ID 顺序处理；通过并发测试确认与文章删除、重新生成、实体合并兼容。
- 复用现有失败重试和崩溃任务回收；对长任务明确超时、分段检查点或续跑方式。旧执行者即使在回收后返回，也不能覆盖已发布的新结果。
- 后台补扫发现尚未安排任务的待更新版本，覆盖提交后进程中断等情况。重试耗尽的同版本保持失败，不通过补扫无限重新创建付费任务；用户重试或新的材料变化可以再次触发。
- `abstract_stale` 在过渡期由版本差异派生，禁止旧代码独立把它清零。队列应持续处理剩余任务，不再依赖下一次 RSS 导入来消化一批之外的实体。
- Wiki 在数据库发布后从当前权威正文写入，使用临时文件与原子替换。渲染也要核对版本并防止迟到写入覆盖较新文件；文件失败可单独重试，不必重新调用模型。
- 页面提供待更新、更新中、失败、已更新的信息和最后完成时间；任务参数、锁和内部表名不进入用户流程。

## 7. 所有入口的迁移清单

| 入口 | 需要改成的行为 |
| --- | --- |
| `article_ingestion.py:_promote_entities` | 晋升及来源登记交给 module，去掉 worker 独立生成、截断和 entity Wiki 写入 |
| `kb/ingest.py:do_process_entity_candidates` | 匹配到已有实体时原子保存贡献并安排更新；已晋升候选回流到原实体，避免再次晋升成副本 |
| `mark_candidate_promoted` / `_materialize_candidate_facts` | 候选关联迁入统一流程，退出“前三条事实拼摘要”的覆盖路径 |
| `kb/graph.py` 的 entity 刷新函数 | 收拢为 module 的兼容调用，最终移除被替代的生成逻辑 |
| `maintenance/entity_ops.py` 的晋升、链接回填与 orphan 检查 | 复用晋升、关联和刷新能力；链接装饰不再成为来源入库的必要前提；区分无来源与无具体事实 |
| `kb/ingest.py:do_reingest` | 原子替换文章旧贡献，同时安排旧、新受影响实体更新 |
| `document_lifecycle.py` 永久删除与 `kb/internal.py` 文章删除入口 | 删除前找出受影响实体，在相同事务中移除贡献并安排更新 |
| `kb/entity.py` 合并、删除、修改名称与手动 regenerate | 合并来源后刷新目标；删除或合并使旧任务失效；名称变化更新正文与元数据；手动刷新返回可查询的任务 |
| `kb/wiki.py`、`kb/internal.py`、`kb/public.py`、`kb_tools.py`、知识页 | entity 正文统一读取已发布完整内容，Wiki 按该内容渲染，维持字段兼容并展示任务状态 |
| `maintenance/restore.py` 与其他恢复入口 | 恢复后的实体来源纳入同一规则，安排更新；旧正文有保留记录但不能自动变成事实依据 |

手动 regenerate 与 `refresh_stale` 当前是同步返回结果；改为排队后，需要更新调用方并明确响应中的“已接收”和“已完成”，不得保留误导性的成功语义。

## 8. 现有数据盘点与修复

先实现可重复执行的只读盘点脚本，再实现有检查点的修复脚本；默认 dry-run，支持指定 entity 与小批量范围。

盘点至少包括：实体数量、有效来源数、facts 与 mentions 的差异、候选晋升状态、已有正文与摘要长度及指纹、正文可读取情况、陈旧标记与任务状态、重复或悬空关联。长度仅帮助发现疑似问题，不把短正文自动判为错误。

修复顺序：

1. 保留现有数据库和 entity Wiki 快照，为每个实体记录原始内容与恢复来源。
2. 从有效 facts、article→entity 的 mentions/历史 wikilink、已晋升候选的文章列表及旧来源元数据恢复来源关联，去重并校验同用户与节点类型。模糊的词语匹配只列为待核对，不能直接补成事实。
3. 将可用的历史完整 Wiki 正文导入独立正文存储并标记待核对；只有数据库短描述的实体如实标记。两者不同不能只以“更长”决定哪个正确，保留两份供修复核对。
4. 以库内可用文章证据重新生成选定实体，验证来源、正文、引用和页面同步。先用少量有代表性的实体验证，再扩展批次。
5. 修复可重入：已完成且输入未变的实体跳过，失败可重试，停止后可继续。报告已修复、缺材料、失败及未处理的数量，保留具体原因。

Schema migration 只新增结构，不在迁移时批量调用模型。生产批量生成前先给出实际实体数、材料规模和 token/费用估算，由用户确认运行范围；本计划编写不代表执行了付费修复或生产变更。

## 9. 实施顺序与完成标准

| 阶段 | 交付内容 | 完成标准 |
| --- | --- | --- |
| E1：复现和盘点能力 | 两篇文章逐次贡献同一实体的失败用例；只读审计；记录当前 HTTP 合约 | 能展示新贡献未进入刷新输入、刷新后页面仍旧的问题；审计能区分短但正确与疑似缺失 |
| E2：来源、正文与版本基础 | Alembic 增量迁移、module、来源操作、正文读取和 entity 渲染 | 来源/facts/边/更新请求原子提交；完整正文保存无字符截断；entity 单节点重建不改变正文 |
| E3：基于证据生成 | 全来源遍历、正文证据读取、章节识别、提示词替换、引用与续写处理 | 不受固定字数和前 N 篇限制；长输出完整；缺材料与未完成输出不伪装成功 |
| E4：可靠任务与全部入口 | jobs 接入、版本保护、持续处理和重试、晋升与维护退役旧路径、删除/重新生成/合并联动 | 不漏更新、不重复晋升、不被迟到任务覆盖；重启后继续；失败对用户可见 |
| E5：读取与兼容、旧数据修复工具 | 页面与工具读取统一、任务状态、dry-run 和分批修复 | 页面正文与权威内容一致；来源变化可追踪；修复可暂停、继续和审计 |
| E6：发布及旧数据验证 | 测试关卡、迁移与部署步骤、选定实体试修复、之后分批处理 | 生产样例符合内容原则，报告覆盖情况与失败项；未完成的数据修复不宣称完成 |

E2–E5 先在同一开发分支完成并验证，再协调发布 API、job worker、ingestion worker 与 web。数据库结构先做增量迁移；新生成路径接管后关闭旧 entity 写入器，防止混合版本继续覆盖正文。代码回退时保留新增正文和修复快照，不执行会丢失新正文的降级迁移。

### 本地实施记录与生产操作

- 增加 `0005_entity_knowledge` 迁移、`kb/entity_knowledge.py`、持久化刷新 job；文章正文定位随 article 保存，书籍章节各有独立正文文件。完整 entity 正文保存在数据库，Wiki 从该正文渲染。
- 晋升、已有实体贡献、重新生成、永久删除、合并、手动刷新和维护晋升已接入统一来源关系。entity 详情、公共读取与工具读取优先使用已发布正文。旧短描述不会覆盖完整正文。
- 第一次新增贡献时会在同一事务中恢复该 entity 可确认的历史来源（facts、mentions、已晋升候选及旧 Wiki 的来源清单），并保存旧 Wiki 正文供新生成对照。旧正文没有作为事实证据直接输入。
- `services/api/entity_knowledge_audit.py` 默认只读；生产镜像内可运行 `docker compose exec api python entity_knowledge_audit.py --limit 50`。使用 `--after <上次输出的 last_entity_id>` 继续下一批。`--entity ent_...` 只查看指定实体。`--snapshot /app/user_data/批次.json` 保存包含旧正文与候选来源的审计快照；文件权限为 0600。
- 只有明确执行 `--apply --snapshot /app/user_data/新文件.json` 才会恢复旧 Wiki 正文与有效来源关联，并把需要重建的 entity 放入后台队列。运行此命令前需先依据只读盘点决定批次范围，并估算模型调用量；本地实施没有对生产运行此命令。代码回退时不要对 `0005` 执行 downgrade，以免丢失新增正文。
- 本地回归入口为 `bash scripts/test_document_lifecycle.sh`；它运行一次性 PostgreSQL 迁移、lifecycle/intake/entity 回归和 ingestion worker 的文章流程测试。生产验收仍需抽查少来源、多来源、重复报道及冲突报道实体，并观察新增文章后的版本与引用。

## 10. 验收与测试

使用一次性 PostgreSQL、临时文件目录和可控制的模型 adapter。自动测试验证数据、流程和发布结果；语言质量另用固定材料样例核对，不能仅靠字数或提示词字符串断言。

| 验收场景 | 必须得到的结果 |
| --- | --- |
| 一篇只讲印度某项政策的文章 | 页面仅覆盖有依据的信息，无库外百科填充；不要求凑够字数 |
| 同一 entity 增加不同方面的第二篇文章 | 同一个实体正文吸收新信息，保留仍有效的旧信息，两者都能追溯来源 |
| 多篇重复报道 | 合并重复事实，保留必要来源；不按文章数量重复章节 |
| 超过原有来源数量上限 | 后加入或排序较后的文章仍进入证据处理，不静默遗漏 |
| 模型返回超过 500/600 字且信息充分的正文 | 数据库、详情接口和 Wiki 均保存完整内容，没有字符切片 |
| 模型因输出额度中止、空响应或引用非法来源 | 续写/重试或明确失败，上次完整正文保持可用，不把半篇内容标为完成 |
| 已有事实但缺 mentions；有有效来源但无具体事实 | 来源能一致恢复；不能把“被提到”扩写成未经材料支持的知识 |
| 新增、重新生成、永久删除文章 | 来源贡献正确加入、替换或移除，受影响实体最终更新，无已删除内容残留在最新版本 |
| 文章已提交但提取正文引用尚未发布 | 刷新等待材料就绪，不误报缺失、不用摘要提前发布不完整正文；就绪后自动继续 |
| 移动和归档文档 | 按现有知识保留规则处理，不因组织位置变化丢失证据 |
| 实体合并或删除时生成仍在进行 | 旧任务不能复活源实体或覆盖目标实体；合并后的重复来源去重 |
| 生成中来了新文章，或两个 worker 重叠执行 | 新请求保留，过时结果不能发布；最新版本最终可见 |
| 数据库中途失败、进程重启、任务超时、文件写入失败 | 无半套来源关联；任务可恢复；正文一致；文件修复不重复生成正文 |
| 待更新实体数超过单批大小，部分任务反复失败 | 后续批次继续，失败任务有界重试，不阻塞其他实体或无限扣费 |
| 书籍章节、旧 Wiki 唯一正文、原文已丢失 | 使用正确章节/证据范围，明确缺失，不将整本书或短摘要冒充章节全文 |
| 维护晋升、直接晋升、entity Wiki 重建 | 同一份正文与来源规则，没有后台旧写入器覆盖 |

把新增 PostgreSQL 测试接入现有测试脚本或明确的实体测试脚本，并更新 `.github/workflows/build.yml` 的触发路径和镜像发布依赖。覆盖 API、ingestion-worker、相关配置与脚本变化；继续运行已有 lifecycle/intake 回归与受影响前端类型检查。

生产验收选取“来源少且信息少”“来源多且信息丰富”“报道重复”“存在更正或冲突”四类实际实体，比较修复前后正文、来源覆盖及新增文章后的更新。最终记录可核对的正文版本和任务结果；仍缺材料或生成失败的实体单独列出。
