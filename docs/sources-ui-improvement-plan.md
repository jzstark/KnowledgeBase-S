# /sources 界面与批量操作实施计划

日期：2026-09-18  
状态：阶段 1 已通过 VPS 验收；阶段 2 已完成本地实现、生产构建和编译检查，待浏览器及 VPS 验收；其余阶段待实施。

## 1. 目标与范围

当前 `/sources` 页面包含四栏：全局导航、资料夹列表、当前资料夹内容、单篇文档详情。用户管理大量文章时存在以下问题：

- 长列表滚动后，右侧详情和操作区离开视口，需要返回顶部才能操作。
- 缺少当前资料夹关键词筛选，定位待整理文章费时。
- 归档、删除、重新生成只能逐篇操作。
- 无法在当前页面方便地为已有文档设置预制内容类型。
- 类型、状态等列被挤压，截图中的“已入库”出现逐字换行。

目标流程：选择资料夹 → 关键词筛选 → 多选 → 执行批量操作 → 查看明确的执行结果。

按功能分阶段实施，每阶段独立提交、部署到 VPS、验收，通过后再开始下一阶段。第一阶段只修布局；搜索、多选、类型修改、重新生成和永久删除依次交付。

本轮约定：

- 保留现有四栏结构，单篇详情和单篇操作入口继续可用。
- 第一版搜索当前资料夹的显示名称、关联文章标题、来源链接，不包含正文、跨资料夹或子资料夹递归搜索。
- “修改类型”指 `doc_kind`：法规、判例、新闻、备忘录、合同、分析、其他。选项取自现有配置接口。
- AI 提取的主题标签 `tags[]` 是另一套数据，本轮不增加其批量编辑。
- 列表选择和批量操作以 `document_instance.id` 为单位，一个文档实例只显示一行；不把其关联的多篇文章误当成多个独立选择目标。
- 不因批量管理需要而扩大 MCP 写权限，不将此工作与其他架构重构合并。

## 2. 已核对的现状与实施约束

以下是基于当前代码的观察。布局原因仍须通过浏览器实际验证；数据行为需要在对应阶段建立测试。

| 位置 | 当前行为 | 对计划的影响 |
|---|---|---|
| `services/web/app/components/AppFrame.tsx` 与 `app/sources/page.tsx` | 外层工作区限高，sources 内层又使用 `min-h-screen` 和 `100vh`，存在嵌套滚动与 flex 高度约束问题 | 阶段 1 修正高度链与滚动容器，不能仅给详情栏加 sticky |
| `GET /api/folders/{id}/contents` | 返回文档实例与 article ID，未补齐前端声明的文章标题和文件信息 | 阶段 2 补齐列表需要的查询字段 |
| 同上 | 直接关联 article 表 | 必须保证文档实例去重，处理一个文档关联多个文章的情况 |
| 文档类型显示 | 页面主要读取 `document_instances.doc_kind` | 类型列空白只说明未显式设置，不证明已有文章没有继承类型 |
| 文档 PATCH | 类型修改仅写 `document_instances` | 阶段 4 同步 source item、文章及相关派生元数据 |
| 文档归档 | 只把 document instance 状态改为 `ignored`，默认列表仍包含该状态 | 阶段 3 定义列表行为并修正队列与订阅同步的一致性 |
| source item materialize | 冲突更新保留 `succeeded`、`deleted`，未同样保护 `ignored` | 已归档状态可能被后续同步覆盖，批量归档前必须修正 |
| 文档 reprocess | 重置为 pending 并触发 worker | 接口成功仅说明提交处理，不能据此判断生成完成 |
| `services/api/kb/ingest.py` | 已存在同一 document instance 的 article 时直接返回 duplicate | 阶段 5 先修正单篇重新生成，确保数据库内容确实更新 |
| 硬删除文件清理 | 直接清理关联原文路径 | 阶段 6 删除前必须检查其他文档是否共享原始资源 |
| 镜像发布与 Watchtower | 各服务镜像独立构建、更新 | 新后端先发布，前端随后发布，必须兼容短暂的新旧版本组合 |

当前资料夹包含数百条记录，且接口本来就全量返回当前资料夹条目。第一版采用前端即时筛选；暂不引入分页、虚拟列表或新的搜索服务。若实际性能验证不达标，再单独评估。

## 3. 阶段总览

| 阶段 | 交付结果 | 主要服务 | 上线门槛 |
|---|---|---|---|
| 1 | 四栏独立滚动与列宽修复 | web | 列表滚到底仍能直接操作详情 |
| 2 | 当前资料夹关键词筛选 | api、web | 搜索准确、无重复条目、无资料夹响应串写 |
| 3 | 多选与批量归档 | api、web，必要的 worker 状态衔接 | 只操作所选项，归档后同步不恢复 |
| 4 | 单篇及批量修改内容类型 | api、web，必要的派生元数据衔接 | 列表、文章与检索过滤一致 |
| 5A | 正确的单篇重新生成 | api、ingestion-worker、web | 内容更新、ID 保留、失败保留旧数据 |
| 5B | 批量重新生成 | api、ingestion-worker、web | 持久化排队、无重复消费、进度准确 |
| 6 | 批量永久删除 | api、web，复用前阶段并发保护 | 删除范围准确、保护共享原文、订阅不复活 |

阶段 4 完成后，日常“搜索 → 多选 → 归档或修改类型”的流程已经可用。阶段 5 和 6 分别独立验证。

- 点击列表底部文章时，右侧更新详情，文章列表保留滚动位置。
- 类型、状态、时间保留合理宽度并禁止逐字换行；标题使用剩余宽度并截断，悬停可查看完整内容。
- 窄窗口优先允许表格区域横向滚动，不能撑坏旁栏或遮住操作区。

## 5. 阶段 2：当前资料夹关键词筛选

### 交互与匹配规则

第三栏顶部增加搜索框，提示“搜索名称、文章标题或来源链接”，显示“匹配 M 条，共 N 条”。

- 对显示名称、关联文章标题、来源链接执行包含匹配。
- 忽略英文大小写和首尾空格；纯空白输入等同于清空。
- 空白分隔的多个关键词采用 AND：每个词都必须匹配至少一个搜索字段，各词可以命中不同字段。
- 不解释正则表达式或通配符。
- 清空搜索恢复当前列表；切换资料夹清空搜索。
- 明确区分资料夹为空、没有匹配结果、加载失败。

### 数据与请求处理

- contents 接口补齐列表需要的文章标题、文件类型等字段。
- 保证每个文档实例一行；若关联多个文章，搜索应覆盖其关联标题，不能仅搜索任意一篇标题。具体采用聚合字段还是等效查询在实施时确定。
- 数量统计按唯一文档实例计算。
- 使用取消请求或响应序号等机制，防止资料夹 A 的迟到响应覆盖已切换到的 B。
- 请求失败时显示错误，不能把前一个资料夹的数据作为新资料夹内容展示。

### 验收

- [ ] 中文、英文大小写、来源链接、多个关键词符合约定。
- [ ] 空白输入、无匹配、空资料夹分别正确展示。
- [ ] 同一文档关联多篇文章时不重复显示，各关联标题可被搜索。
- [ ] 切换资料夹重置搜索；快速切换不会串数据。
- [ ] 数百条记录输入筛选流畅。
- [ ] 搜索不会修改任何文档数据。

## 6. 阶段 3：多选与批量归档

### 选择规则

- 行复选框控制批量选择，点击文章行控制右侧详情，两者状态独立。
- 表头复选框全选当前筛选结果，支持全选、部分选中、未选中状态。
- 筛选变化时保留仍可见的选择，移除不可见选择；扩大结果范围不自动选中新出现的条目。
- 切换资料夹清空选择。
- 操作后刷新时，删除已消失或不再可选的 ID，不能保留失效选择。
- 第三栏固定区域显示“已选择 N 条｜归档｜取消选择”。

### 归档语义与后端

归档用于整理资料夹列表，保留原文和已有知识文章；已有文章仍可被知识库和 MCP 检索。默认列表隐藏已归档项，增加“显示已归档”开关。此时显示数、搜索结果数均基于当前可见范围。

- 同步更新 document instance 与关联 source item 的状态。
- 订阅重复列出条目时保留归档状态，普通轮询不能重新排队。
- 正在处理的条目返回不可归档原因，不中途取消正在执行的生成。
- 归档与 worker 领取任务之间通过条件更新或等效机制保证互斥，防止刚归档又被领取。
- 仅前端检查 processing 不够，后端在实际修改时重新校验状态。
- 单篇和批量归档共用业务逻辑。
- 已归档项重复归档返回明确的已完成或跳过结果。

批量接口接收明确 ID 列表，逐项返回成功、跳过或失败原因。每个目标内的关联更新保持事务一致性；一个目标失败不使其他目标的结果丢失。

### 验收

- [ ] 行点击与勾选互不干扰，表头半选状态正确。
- [ ] 筛选 8 条、选择 3 条，仅归档这 3 条。
- [ ] 切换资料夹或改变搜索不会操作隐藏选择。
- [ ] 成功项取消勾选，失败项保留并显示原因。
- [ ] 归档后刷新、立即同步、后续订阅抓取均不恢复。
- [ ] 已有知识文章仍可检索，原文仍保留。
- [ ] 并发领取与归档测试通过，processing 条目得到明确反馈。

## 7. 阶段 4：单篇及批量修改内容类型

### 交互

- 右侧详情增加“修改内容类型”，批量操作栏增加同名入口。
- 下拉选项来自 `GET /api/config/doc_kind`。
- 确认框显示所选条目数量和目标类型。
- 第一版只支持显式设置一种预设类型；“其他”是实际类型，不等于清空。
- “清除覆盖、恢复继承”后置，不在第一版混入空值语义。
- 修改分类不触发模型调用，也不自动重新生成文章。
- 页面区分未设置覆盖与已有文章的实际分类，至少在详情中解释类型来源。

### 一致性要求

每个文档的数据库修改放入同一事务，同步：

1. `document_instances.doc_kind`。
2. 关联 `source_items.doc_kind`。
3. 关联 article 的 `knowledge_nodes.doc_kind`，包括一个文档关联多篇文章的情况。
4. 相关摘要的类型元数据，使按类型搜索摘要时不与文章分类分裂。

摘要跟随文章分类的规则需要同时覆盖后续新建、重新生成摘要的路径，不能只修一次批量更新。

- 人工类型在后续订阅同步、重新处理后应保持；核对所有可能覆盖它的路径。
- 处理中条目暂不接受类型修改，后端实际写入时校验，避免被入库覆盖。
- 非法类型返回明确校验错误，不能静默改成默认类型。
- 单篇与批量类型设置共用同步逻辑，检查仍保留的其他类型编辑入口不会造成反向不一致。
- 数据库作为分类依据。Wiki 文件头中的派生类型同步需明确失败补偿方式，不能因只改分类而重新生成正文或向量，也不能声称数据库事务覆盖文件写入。

### 验收

- [ ] 单篇、批量类型设置均正确；未选中的条目保持原值。
- [ ] 列表、详情、关联文章及相关摘要分类一致。
- [ ] 无已生成文章的条目也可设置，后续入库沿用人工类型。
- [ ] 订阅同步及重新处理后人工设置仍保留。
- [ ] 数据库关联更新失败时，单个目标整体回滚。
- [ ] Wiki 派生元数据同步失败可发现、可补偿。
- [ ] MCP 按类型过滤的文章和摘要结果均符合新分类。
- [ ] 修改类型没有新增 LLM 调用。

## 8. 阶段 5：重新生成

### 5A：先修正和验证单篇行为

当前重置 pending 后重新执行 pipeline，并不意味着已有 article 数据更新。需明确区分失败重试与已入库文章的重新生成。

目标行为：

- 保留 article ID，更新文章分析结果、标签、向量和相关派生数据。
- 默认摘要按明确规则更新，保留用户额外创建的自定义摘要。
- 实体关系、事实、候选统计不因重复处理同一文章而不断累加。
- 生成失败保留上一版可读取的知识，不先删除旧文章再调用模型。
- 普通抓取保持去重；显式重新生成走可追踪的更新路径。
- 根据关联 source item 的真实 `source_id` 触发处理，避免移动资料夹后错误推导来源。
- 手动触发与定时轮询不得同时消费同一个条目；对 processing、deleted、缺少可用来源或原文的目标返回明确结果。

重新生成意图必须持久化，以便触发失败后的轮询仍能正确处理。实施 5A 时检查现有任务能力，选择最小的持久化方案：复用现有任务机制，或增加必要字段及 Alembic 迁移。不能只靠一次临时 HTTP 参数，也不在本计划阶段预先搭建新队列系统。

5A 验收：

- [ ] 已有文章重新生成后，数据库字段实际更新，而非仅返回旧 ID。
- [ ] article ID 保留，既有链接仍可使用。
- [ ] 默认摘要更新，自定义摘要保留。
- [ ] 重复生成不制造重复摘要、关系或统计累计。
- [ ] 模型或写入失败时，上一版文章仍可读取。
- [ ] 普通订阅抓取继续去重。
- [ ] 手动触发与轮询并发时，同一条目只执行一次。

### 5B：批量提交与进度

5A 验收后再开放批量重新生成：

- 确认框显示数量，说明会调用模型并产生费用。
- 先持久化处理请求，再按真实来源合并触发 worker。
- 已排队、处理中的条目跳过，不重复入队。
- UI 区分已提交、待处理、处理中、成功、失败；接口接受请求不等于生成完成。
- 存在待处理条目时有限轮询，切换资料夹、离开页面或任务结束后停止相应轮询。
- 请求已持久化但触发失败时显示等待后续轮询处理，并保留可诊断信息。
- 批量受理逐项反馈；完成结果由后续后台状态决定。

5B 验收：

- [ ] 同批多个条目可正常排队，未选中条目不受影响。
- [ ] 重复点击、触发重试不导致重复处理。
- [ ] 触发失败后 worker 轮询能继续处理持久化请求。
- [ ] UI 准确区分提交成功与生成成功。
- [ ] 中途失败逐项展示，不误报全部完成。

## 9. 阶段 6：批量永久删除

### 交互与执行

- 删除作为独立危险操作入口，与归档分开。
- 确认框显示所选文档数量、关联文章与摘要的删除范围，并提示不可恢复。
- 确认提交时重新校验目标和状态；若影响范围发生实质变化，重新展示范围后再确认。
- 处理中条目不能删除，复用任务领取与管理操作间的并发保护。
- 使用有上限的小批次顺序处理并显示进度，批次大小通过实际执行耗时确定。
- 网络中断显示结果待核实，刷新服务器状态后再重试，不能自动认定整批失败或成功。

### 删除语义

- 删除所选文档关联文章、摘要、相应派生文件和关系，并处理现有非外键引用的清理。
- 原始资源有其他文档引用时保留；检查资源 ID 和实际文件引用，不能只按当前文档的路径直接删除。
- 保留 document instance 与 source item 的删除墓碑，订阅同步不得复活。
- 单篇和批量删除共用经过验证的业务逻辑，已删除目标重试返回明确结果。
- 数据库删除与文件删除分别处理失败；数据库事务不能撤销文件删除。
- 对部分清理失败保留可诊断、可重试的结果，不能报告完整成功。

### 验收

- [ ] 普通文档、带多个摘要文档删除范围正确。
- [ ] 未选中文档与自有派生数据不受影响。
- [ ] 共享原文仍能被其他文档访问。
- [ ] 订阅再次列出相同条目后不复活。
- [ ] processing 条目被拒绝，不能与 worker 并发删除。
- [ ] 部分失败、重复提交、网络中断后的结果可核实、可重试。
- [ ] 数据库或文件清理失败不会被报告为全部成功。

## 10. 共用接口、状态与错误约定

以下约定在需要的阶段逐步落地，不提前搭建通用批处理框架。

- 批量请求使用明确的 document instance ID 列表，按 ID 去重，限制请求规模；不让后端按搜索词临时重新确定目标。
- 提交时固定目标快照，执行中防止重复提交。
- 后端校验目标存在性、用户可访问范围、所属资料夹约束和当前状态；采用现有用户登录认证，不开放 service token 或只读 MCP 的管理权限。
- 返回逐项结果及汇总数量。结果至少能表达成功、跳过、失败，以及可理解的原因。
- 各操作使用明确的专用路由或等效清晰设计，共用必要的目标校验和业务函数，不从批量函数循环调用 HTTP 单篇端点。
- 单个目标内的数据库关联更新保持一致，多个目标允许部分成功并明确反馈。
- 前端成功后更新列表和资料夹计数，保留适用的搜索、滚动位置，清除成功项选择。
- 后端仍会重新校验前端已经禁用的操作，防止加载后状态变化。
- 操作失败不静默吞掉；网络中断且无法确认结果时显示未知状态并重新查询。

## 12. 发布、兼容与回退

### 每阶段流程

1. 实现该阶段范围并完成本地验证。
2. 单独提交，确认实际需要的镜像构建成功。
3. 按兼容顺序更新 VPS，核对实际运行版本。
4. 用真实资料夹和专门的测试文档执行该阶段验收。
5. 记录结果与遗留问题，验收通过后再进入下一阶段。

### 服务更新顺序

Watchtower 已恢复，各服务可能在不同时间更新：

- 新 API 先发布，兼容旧前端；VPS 确认 API 可用后再发布新前端。
- 阶段 5 安排 API、worker、web 的兼容顺序；如有迁移，先增加向后兼容结构，再启用新路径。
- 不能假设一次提交中的多个镜像会同时部署完成。
- 保持现有自动更新机制，不重新引入长期手动修改 `.env` 的版本流程。

### 回退与运维边界

- 前四阶段预计不需要 schema 迁移；阶段 5 如需迁移，优先新增兼容字段，避免破坏旧版本。
- 阶段 3 起，服务镜像回退不会撤销已执行的数据修改；验收应先用少量测试条目。
- 阶段 6 前保留数据库与相关原始、派生文件备份；仅回退代码不能恢复永久删除的数据。
- 更新前记录当前运行镜像的可恢复版本或 digest，确认回退镜像仍可获取；不能依赖 `latest` 或会被自动清理的本地旧镜像。
- 单实例容器重建可能短暂中断请求，不承诺零停机。
- 每阶段回归现有单篇操作、上传、订阅处理及 MCP 读取调用；OAuth 和 Cloudflare 配置不属于本轮改动。
