# Document intake 重构方案

状态：实施完成，待 CI 与发布后验证。上传、URL、来源条目接收和连接器关联已迁入 intake module；相关 PostgreSQL 测试已在本地通过。

领域词汇以 [CONTEXT.md](../CONTEXT.md) 和 [资料夹设计](revision-source-folders.md) 为依据。事务与旧 ID 映射的历史问题见 [Phase C 计划](phase-c-convergence-plan.md)。本方案承接已实施的 [Document lifecycle 重构](document-lifecycle-refactor.md)。

## 目标与范围

让一次文档接收操作负责完整建立原始材料、文档实例和来源条目的关联。对需要三种记录的导入路径，成功意味着三者已经关联并提交；数据库写入失败时，本次数据库修改全部回滚。

document intake module 负责接收和建立关联。document lifecycle module 继续负责领取、状态回调、重试、重新生成、归档与永久删除。导入时对已有记录的更新必须遵守 lifecycle 的状态保护和锁定顺序。

覆盖这些入口：

- 资料夹上传文件、添加 URL：`routers/folders.py` 的 `upload_to_folder`、`add_url_to_folder`。
- 来源条目接收及文档关联：`routers/sources.py` 的 `_create_source_item`、`_ensure_document_instance_for_source_item`，以及调用它们的 `create_source_items`。
- 旧 source 上传和 URL 接口：`upload_to_source`、`add_url_to_source`。它们与资料夹入口共享接收能力，并保留各自的 HTTP 合约。

旧 ID 后缀约定先集中管理。数据库外键迁移、历史孤儿记录修复、folder/source 创建流程、复制和移动文档的整体改造，另行制定方案。这里的三种记录并非全局一对一：合法的 legacy source item 可能没有关联文档，多篇文档也可能共享原始材料。

## 当前问题与证据

1. `upload_to_folder` 先写磁盘文件，再分别写入 `raw_assets`、`document_instances`、`source_items`，没有包住这些数据库写入的事务。后面的写入失败，会留下此前已提交的记录和文件。
2. `add_url_to_folder` 每次生成新的 raw asset 和 document instance，再按来源唯一键 upsert source item。同一资料夹重复添加相同 URL 时，会复用旧 source item，并把它的文档关联改到新实例；旧实例失去这条处理记录的关联。
3. `_create_source_item` 先 upsert source item，再由 `_ensure_document_instance_for_source_item` 根据 ID 后缀查找 folder/connector、创建原始材料和文档，最后回写关联。这些步骤也没有组成一次完整事务。
4. 旧 source 上传入口同样在数据库写入前保存文件，失败时缺少对应清理。数据库回滚本身不能撤销文件写入。

以上来自代码检查。实施时应先用真实 PostgreSQL 重现失败场景，再将测试作为修复依据。

## 身份规则与已定决定

已有领域依据明确支持：

- 手动重复上传同内容文件可以产生新的文档实例，不按内容哈希强制合并。
- 连接器重复接收同一来源条目应去重，文档移动不改变其来源身份。
- 当前 source item 唯一键为 `(user_id, source_id, origin_ref_type, origin_ref)`。本次先保留这套来源识别方式，不增加 URL 规范化或跨连接器合并规则。

**采用 A：同一资料夹重复添加相同 URL 时复用已有来源条目及文档关联。** 不新建文档，不重新排队，也不将旧 source item 改挂到新文档。`pending`、`processing`、`succeeded`、`failed` 均返回已有记录；失败后的重试通过显式操作发起。已归档或删除的 URL 返回 409，已移出资料夹的文档也返回 409，不隐式复活或移回。旧 source URL 接口同样复用来源条目，不在重复接收时触发 worker。两个 URL 接口均保留 `urls_queued`，并新增 `urls_reused`；资料夹页面分别提示新排队和已存在的数量。

原实现不能作为正确重复行为的基线直接保留；本次测试复现了旧文档关联被替换的问题，并验证了上述行为修正。

## Module 与 interface

新增 `services/api/document_intake.py`，采用一个 Python module，集中身份判断、写入协调和接收结果。先按实际调用意图提供少量操作，具体函数参数在实施时按现有调用所需信息确定。

| 调用意图 | interface 承诺 | implementation 负责 |
| --- | --- | --- |
| 接收上传文件 | 返回已提交的文档和来源条目关联 | 保存本次文件、生成身份、原始材料信息、类型和时间字段、数据库关联与失败清理 |
| 接收手动 URL | 返回新建或复用的完整接收结果 | 已确认的重复规则、身份与关联、初始处理状态 |
| 接收连接器或 legacy source 条目 | 返回已有或新建的 source item 及合法文档关联 | 来源唯一键、冲突处理、旧 ID 映射、已有记录保护及缺失关联的建立 |
| 协调一批输入 | 按现有 HTTP 合约返回结果 | 逐项提交、已成功项的保留、提交后的 worker 通知 |

HTTP route adapter 保留认证、请求解析和响应映射。module 不依赖 FastAPI 请求对象；调用者无需自行计算关联 ID、串联三张表或决定数据库提交与 worker 通知的顺序。

文件存储与 worker HTTP 调用沿用现有方式。测试使用临时文件目录和可控制成功、失败的 worker adapter；不为未来存储方式增加通用框架。

## 事务、并发与批量行为

1. 每份输入有独立数据库事务。新建时创建相关记录并建立关联；去重命中时，合法的字段更新和关联维护也在同一事务内完成。
2. 用现有唯一约束协调相同来源的并发接收，冲突时读取真实已存在记录。返回实际提交的 ID，不能把本次预生成但未使用的 ID 当成成功结果。
3. 重复接收不得覆盖 ignored/deleted 终止状态、抢走正在处理的关联，或清除已持久化的 regeneration intent。已有记录的状态更新需逐字段检查，避免用整行 upsert 重置状态。
4. 与 lifecycle 交错时统一锁定顺序：关联文档在前、相关 source items 在后；读取关联后加锁并复核。首次创建和唯一键冲突路径也要纳入锁协议设计，不能以先锁 source item 再锁已有文档的方式形成反向等待。
5. 多文件或多 URL 逐项提交，后续项失败不回滚前面已成功的项。保留当前停止处理及错误响应方式；本次不默认增加“继续全部处理并返回逐项失败”的 HTTP 协议。
6. 需要主动触发 worker 的入口在数据库提交后通知。同一批按实际 source 合并通知；后续输入失败时，已提交项仍可由 worker 轮询处理。仅接收条目的内部接口沿用其现有调度方式。
7. worker 通知失败不撤销已提交的数据，不能把已接收资料报告成未保存。保留各入口既有响应字段，测试实际待处理状态和轮询可见性。

## 文件保存与失败处理

- 上传只创建本次操作拥有的新文件；文件写入失败时不提交文档记录，并清理可能的部分文件。
- 数据库事务确认回滚后，清理本次上传创建且未被成功记录引用的文件。不得删除来源条目引用的既有文件、共享文件或连接器传来的文件路径。
- 数据库提交成功后保留文件。若提交结果因连接中断而无法确认，先核对持久化结果再决定清理，避免删除已经入库的材料。
- 清理自身失败时，记录可定位的路径与原始操作错误，向调用方表达失败；不能把“数据库回滚”宣称为“文件清理成功”。本次不承诺进程崩溃或主机断电后自动清除所有孤儿文件。

## 兼容约束

- 除明确确认的重复 URL 行为修正外，保留现有 HTTP 路径、响应结构、状态码、字段默认值和文件保留策略。
- 保留来源信息与资料夹组织关系的区别；移动过的连接器文档不得因重复接收回到旧资料夹。
- 保留旧 source 接口与 worker 调用，不假定所有 source 都有可映射的 folder 或 connector。
- 对合法的无关联 legacy 条目继续提供兼容；遇到超出兼容规则的历史悬空关联时应报告问题，不在请求里自动修复或删除历史数据。
- 不改变已完成的 lifecycle 状态语义，不通过重复导入绕过显式重试、重新生成或终止状态保护。

## Test surface 与验收

复用 lifecycle 的一次性 `pgvector/pgvector:pg16` 测试基础设施和 Alembic 迁移，通过 intake module 的 interface 检查实际数据库与文件结果。测试不访问生产库、真实用户资料或模型服务。

| 必须通过的行为 | 验证方式 |
| --- | --- |
| 创建或关联的任一步数据库写入失败 | 在真实 PostgreSQL 注入失败，确认本次记录和字段更新均回滚，既有记录保持原值 |
| 文件写入或持久化失败 | 使用临时目录，确认本次文件被清理，既有文件与共享文件仍在 |
| 文件清理失败 | 确认数据库已回滚，错误可定位，不返回虚假的导入成功 |
| 重复手动上传 | 同内容文件导入两次，得到各自合法的文档及处理关联 |
| 重复手动 URL | 按最终决定验证新建或复用，旧文档关联不会被意外替换 |
| 重复与并发连接器输入 | 独立连接同时接收同一来源条目，只产生一组应有记录，返回同一个真实关联 |
| 接收与 lifecycle 竞争 | 控制接收与领取、归档、删除的交错顺序，确认无复活、关联替换或死锁 |
| 先移动后重复接收 | 来源身份保持一致，已有文档保留目标资料夹 |
| legacy source 无 folder 映射 | 保留合法的 source item 结果，不错误创建文档或拒绝原本支持的路径 |
| worker 通知失败或批量中途失败 | 已提交项仍可查询和轮询，未提交项无残缺记录，HTTP 行为符合既定合约 |
| 新接收资料进入后续流程 | 文档可由现有 worker 领取，并可通过 lifecycle 重新处理、归档和删除 |

并发测试使用独立连接、显式同步点和有限超时。保留 HTTP 合约测试；真实数据库测试覆盖后，替换本次迁移涉及的 SQL 字符串断言，避免测试绑定代码位置。

## 实施顺序与完成标准

1. 明确重复 URL 决定并记录各入口的当前合约；建立失败与重复输入测试。完成标准：部分写入和 URL 关联替换问题可重复展示，目标行为有明确断言。
2. 落地 module，迁入资料夹上传及文件失败清理。完成标准：三张表原子写入，上传失败无本次残缺记录，并通过文件清理测试。
3. 迁入 URL 接收并实现已确认的重复规则。完成标准：重复输入不会错误替换关联，相关页面和旧入口合约通过。
4. 迁入连接器条目接收及旧 source 上传入口，统一去重、关联和锁协议。完成标准：并发接收及与 lifecycle 交错测试通过，legacy 路径仍可使用。
5. 补齐批量与 worker 通知测试，移除本次迁移产生的重复 implementation，接入现有 CI 关卡。完成标准：intake 与 lifecycle 测试通过，相关镜像发布必须等待两者成功；脚本和 workflow 变更也触发检查。
6. 发布后用可丢弃的测试资料验证上传、URL、连接器接收以及后续生命周期操作。完成标准：服务健康、实际文档关联与确认的重复行为一致。文档编写本身不代表已授权发布。

旧 ID 外键化和历史数据清理不作为以上步骤的隐含内容；如实施发现它们是必要前提，应先补充具体数据与影响证据，再调整本方案。
